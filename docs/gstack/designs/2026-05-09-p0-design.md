## Problem Statement

中国互联网平台（B 站、小红书）是信息孤岛。收藏的视频和图文内容被锁在平台内，不能被本地工具（Obsidian、LLM、搜索）消费。现有商业产品（Get 笔记）不开源、数据不可控。开源世界里 BiliNote 做了 B 站 + YouTube → Markdown，但不覆盖小红书。没有人做 **B 站 + 小红书 → 本地 Markdown** 这个组合。

## What Makes This Cool

这是一个**开源的中国社交媒体内容解放工具**。粘一个链接，本地多一个 Markdown 文件。简单、可靠、数据在你手里。更酷的是——它是管道层，上面可以接 OpenClaw、Claude Code、Obsidian 知识图谱、博主创作分析等任何东西。

## Constraints

- 上游依赖 social-post-extractor-mcp 是 Alpha（5 星 21 commits），需要 fork 后自己维护
- 部署在本地服务器（国内 IP），通过 tailscale 远程访问
- 百炼 API Key 是 P0 唯一模型后端

## Premises

1. B 站 + 小红书 → 本地 Markdown 是一个值得做的独立开源工具，因为没有竞品覆盖这个组合
2. 上游 social-post-extractor-mcp 作为 P0 骨架足够稳定
3. "开源给更多人用"意味着安装体验和文档跟代码同等重要
4. P0 极简（不做批量/博主全量/评论）是正确的——先把单链接转换做可靠
5. 百炼作为唯一模型后端在 P0 合理，开源后必须支持其他模型

## Cross-Model Perspective

Codex 独立审阅后的判断：

- **Coolest version:** "开源基础设施，把中国社交媒体变成个人的、模型可读的记忆。" 不只是转文字，是构建可版本化、可搜索的本地知识图谱。
- **Key insight:** 用户说"这只是一个前端接口"——兴奋点不在爬取，在于**封闭平台和强大推理系统之间的管道**。
- **50% project:** BiliNote 证明了 B 站 → Markdown 的可行性（FastAPI 架构、开源打包），缺的 50% 是小红书支持、模型后端抽象、中国平台特有的失败处理。
- **Weekend prototype:** 只做 CLI `rbcp run <url>`，两条 happy path（一条 B 站视频、一条小红书图文）。

Claude 与 Codex 共识：P0 极简路线正确，CLI 优先，BiliNote 是最近的开源参考。
Claude 补充：用户现有的 SPEC 目录结构（按作者归类）比 Codex 建议的按 ID 归类更利于知识管理。

## Approaches Considered

### Approach A: 严格按现有 SPEC 执行（chosen）

PRD/SPEC/PLAN 已成熟，直接按图施工。M0 验证上游 → M1a CLI → M1b WebUI。

- Effort: M（约 4 天）
- Risk: Low
- Pros: 文档已有、路径清晰、不走弯路
- Cons: 不会产生新的设计洞察
- Completeness: 9/10

### Approach B: BiliNote 参考架构

先研究 BiliNote 代码，借鉴安装体验、Docker 打包、本地 Whisper 集成，保持自己的技术栈。

- Effort: L（多 1-2 天研究）
- Risk: Medium（可能被别人的设计干扰判断）
- Pros: 开源包装经验可复用、避免踩坑
- Cons: 多花时间、可能过度参考
- Completeness: 8/10

### Approach C: CLI-first 极简版

只做 CLI，不做 WebUI，先开源纯 CLI 工具。

- Effort: S（约 2 天）
- Risk: Low
- Pros: 最快发布、CLI 对 AI Agent 友好
- Cons: 非开发者用户不会用
- Completeness: 6/10

## Recommended Approach

**Approach A**。文档体系已经非常成熟（PRD/SPEC/PLAN 三件套），直接执行是最高效的。不需要额外研究，不需要砍范围。Codex 建议的 "Weekend prototype"（只做 CLI）本质上就是 M0+M1a，我们不单独做一个 prototype 阶段，直接按 PLAN.md 顺序执行。

**目录结构决定：** 采用用户偏好的扁平风格，同时保留 ID 后缀防冲突：

```
~/transcript/
├── bili/YYYY-MM-DD-UPName-Title-BVxxxx.md
├── xhs/YYYY-MM-DD-Author-Title-noteId.md
├── xhs/YYYY-MM-DD-Author-Title-noteId.comments.md
└── _index.sqlite
```

与 SPEC §6.1 的差异：根目录从 `~/knowledge-vault/` 改为 `~/transcript/`，去掉作者子文件夹（扁平化），分隔符从 `_` 改为 `-`。sanitize 规则和原子写入逻辑不变。需要同步更新 SPEC §6.1 和 PRD §5.1。

## What I noticed about how you think

- 你在动手写代码之前花了大量时间做文档——PRD、SPEC、PLAN、CLAUDE.md、LOG、REFERENCES 六份文档，还没写一行 Python。这是工程纪律，不是拖延。
- 你说"这只是一个前端接口"的时候，其实暴露了你真正的野心：不是在做一个小工具，而是在搭一个管道基础设施。
- 目录结构你立刻有自己的意见（`~/transcript/` 而不是 SPEC 里的 `~/knowledge-vault/`），说明你对最终产物的形态有清晰的品味——不想让命名比它实际的作用更宏大。
- 把项目命名为"红蓝 CP"而不是什么"AI Knowledge Extractor"——有趣、有记忆点、有文化梗。这是产品直觉。

# 0.6 M6 全链路建成 + 桌面端能力缺口复盘

> 一句话：0.6 引擎（Extract+Digest）+ CLI 建成并真链路验证、扎实；**Desktop 只做成了"速览查看器" spike，缺 V0.5 WebUI 的全部交互能力——这是本次明确的欠交付，GUI 设计交还用户**。

## 背景

按 [0.6 实现计划](2026-06-15-0.6-implementation-plan.md) 锁定的契约，一下午把 M6 全部子里程碑做完并合进 `feat/0.6-extract-digest-render`（~16 提交）。全程按 ultracode 用 dynamic workflow 编排（设计/验证/并行）。收尾时用户指出 Desktop「设计得像个残废」——属实，记录于此。

## 完成了什么（M6 全链路）

引擎与 CLI（扎实、已验证）：
- **M6-pre**：`service/`→`extract/` 机械改名 + 弃用 re-export shim。
- **§A/§B/§C 契约**：dataclass 桩 + import-lint（digest 只依赖 `app.extract.contracts`）；经 4-lens 对抗审查补强（2 blocker+4 major）。
- **M6a**：`app/config.py` platformdirs 配置发现，修「`~/.config/rbcp/.env` 从未被读」硬伤 + PR#46。
- **M6b**：`ExtractResult` 迁冻结契约（canonical 原文 + readable 清洗版 + text_sha256 + 句级 segments，char 对齐）；`build_canonical_text_and_segments`。**真链路**：B站视频 44 段 char 对齐、毫秒坐实、.md 正文=清洗版。
- **M6c**：`app/digest/` digest() = LLM 三形态 + 确定性服务端锚定（exact→normalized、低置信进 diagnostics、HIGHLIGHT_MIN_CONFIDENCE=0.7）；3-lens 对抗验证修 2 major（normalized 1→N 越界、segment_id 压 context）。**真链路**：`rbcp digest <url> --json` 端到端，highlights 全 exact + 真时间戳。
- **M6f**：`rbcp digest <url> [--json]` + `rbcp ls` + 门面动词接线。

验证：566 测试；两条真链路；design-panel / 对抗验证 / fan-out 三类 workflow 编排。

## 现象 / 欠交付：桌面端是"残废"

**Desktop（M6e+d）只做成了一个最小"速览查看器"**：Tauri v2 壳 + PyInstaller sidecar + 前端渲染**一份** digest 的三形态（高亮/卡片/脉络）。它**没有** V0.5 WebUI 的任何交互能力：

| V0.5 WebUI 能力 | Desktop 现状 |
|---|---|
| 粘 URL 提交单条、看任务列表（2s 轮询）| ❌ 无（前端只读 sample.json）|
| 批量导入 notes.json / 批次进任务列表 / 逐条建 job | ❌ 无 |
| 博主全量清单（`/api/uploaders/posts`）| ❌ 无 |
| 评论抓取（`/api/comments`）| ❌ 无 |
| 任务详情 + Markdown 渲染/源码切换 + 下载 | ❌ 无 |
| 用量/费用账单、累计费用 | ❌ 无 |
| 去重检测（dedup_key，409 弹窗）| ❌ 无 |
| 失败重试、错误分层展示 | ❌ 无 |
| 历史/搜索/最小 Library | ❌ 无 |

「▶ 跑引擎」按钮也只是 spawn sidecar 跑一份 demo，不接真实 URL/provider（FakeProvider + 桩 extract）。所以它看起来、用起来都像残废——因为它就是个渲染 spike，不是产品壳。

附带两个已修的小问题：
- **没 DESIGN.md → spike 跑偏**：fan-out agent 没有设计系统可继承，自起一套暗色 generic UI。已补 `DESIGN.md`（归纳 WebUI 的「红蓝品牌」为单一真相源）+ 把 Desktop 重皮成红蓝亮色。
- **sidecar 路径**：`build.sh` 没把二进制放到 Tauri externalBin 期望的 `binaries/rbcp-sidecar-<triple>`，`cargo tauri dev` 报 resource 缺失。已让 build.sh 自动放置。

## 理由 / 根因

把「M6e+d Desktop」当成了**最小可行 spike**（证明 Tauri+sidecar+三形态渲染这条路通），契约/计划里 Desktop 的措辞也是「最小 Library」。fan-out 时给 Desktop agent 的指令就是"最小可用、渲染 sample"。结果：技术路线证明了（sidecar 体积/冷启动 spike 有结论、端到端能跑），但**产品完成度远低于用户预期的"WebUI 全能力桌面版"**。

更深的失衡：一下午的 rigor（多个 workflow、对抗审查、真链路）几乎全压在**看不见但承重的引擎**上；用户能看见、最在意的 Desktop 反而只给了最薄一片。这是 scoping 与投入分配的失误，不是技术不可行。

## 影响

| 文件/模块 | 影响 |
|---|---|
| PLAN.md | M6 标"建成+验证"，但 Desktop 完成度需降级标注为"速览 spike，非全功能壳" |

| 代码 | `app/extract` `app/digest` `app/cli.py` 引擎+CLI 扎实；`desktop/` 仅速览 spike |
| 引擎/契约 | 已就绪，可支撑任意 GUI：`rbcp digest --json` + [digest-json 契约](../contracts/0.6-digest-json-contract.md) + WebUI 那套 `app/web/routes.py` 端点 |

## 后续 / 复盘

- **GUI 设计交还用户**（用户明确要自己设计）。设计输入已备齐：`DESIGN.md`（红蓝系统）、`docs/contracts/0.6-digest-json-contract.md`（digest 输出形状）、`app/web/routes.py`（WebUI 全能力端点清单 = Desktop 该对齐的功能面）。
- Desktop 要成产品，需求级问题待用户拍：Desktop 是"WebUI 的桌面壳（全能力，HTTP 调本地 serve / sidecar）"还是"只做速览这一件、其余留 WebUI"？当前 spike 默认了后者的最薄版，用户倾向前者。
- 教训：用户能看见的、最在意的那一面（GUI），不该在 fan-out 里被压成最薄 spike；scoping 要按"用户价值可见度"分配投入，而非按"技术难度"。

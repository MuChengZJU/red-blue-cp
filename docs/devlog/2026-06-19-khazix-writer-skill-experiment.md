# 实验：用「卡兹克写作」skill 写一篇 0.6 发版反思公众号文

> 一次 AI 写作风格迁移的尝试与诚实复盘。文章本身写完了、四层自检全过，但作者读完第一反应是「这不像我写的」。这条「不像」才是本文真正想记的东西。

## 在做什么

0.6 发版后，想写一篇公众号长文，聊的不是产品，而是「一个非纯开发背景的人用 AI（Claude Code）把产品做出来，过程里自己到底扮演了什么角色」——核心是个自我怀疑：我好像全程只是个「提 bug 的人」，把问题甩给 AI 让它调研，自己很少给解法；但回头看，方向是我定的、AI 调研错了是我纠正的、真机的坑是我撞出来的。所以「提问/纠错/真实世界反馈」会不会才是 AI 时代最不可替代的人类角色？

用了开源的 [khazix-skills](https://github.com/KKKKhazix/khazix-skills) 里的 `khazix-writer`（数字生命卡兹克的公众号文风 skill）来生成。素材来自本仓 `docs/devlog/`，开放问题 1 的硬核依据是 [Codex vs DynamicWorkflow 复盘](2026-06-19-codex-vs-dynamicworkflow-orchestration.md)。

## 实验结论（这条是重点）

**风格 skill 迁移的是「文风」，不是「你的声音」。**

`khazix-writer` 把卡兹克的可形式化特征复刻得很到位：禁用词/禁用标点（无冒号、无破折号、无双引号）、一句一段的断裂节奏、`？？？`/`。。。`情绪标点、口语转场、契诃夫之枪式首尾回环、四层自检。这些是**规则**，能机械执行、能自检，迁移得很准。

但「像不像作者本人」靠的是另一层东西——真实的语气惯性、词汇偏好、思维跳跃方式、什么该详什么该略的取舍。这层 skill 给不了，因为它复刻的是**卡兹克**的声音，不是我的。结果就是：一篇合格的「卡兹克风」文章，读起来像卡兹克，不像我。

**可复用的判断**：
- 风格 skill 适合「我没有成型文风、想借一个成熟壳子快速出稿」，或「明确就想要某人那个味儿」。
- 不适合「我已经有自己的声音、想要更像我」——那种情况下 skill 是干扰，正确做法是喂自己的历史文章做少样本、或只用它的 L1/L2 硬规则做校对、内容和语气自己把控。
- 中间路线：拿 skill 的产出当**结构和素材初稿**，人再用自己的话重写一遍（这也正是 skill 自己写的「理想协作流程」里那步「人二次改写，加入自己的声音」——我这次跳过了那步，所以不像）。

### 我用 AI 做完一个产品，才发现我全程就是个「提 bug 的人」

事情是这样的。

昨天半夜，我盯着屏幕，又一次敲下了「还是不行」这四个字。然后顺手把一坨红色的报错粘了上去。

这大概是这一周里，我第 N 次干这件事了。N 是多少我已经数不清。白天是「转录又 400 了」，晚上是「点开桌面客户端，未知错误」，凌晨是「这个模板它说找不到」。我就像一个不知疲倦的复读机，把一个个问题甩出去，等另一头把它解掉。

另一头，是 Claude Code。

今天，我把这个折腾了好一阵的小东西开源了，叫 Red Blue CP，红蓝CP。一句话，粘一个 B 站或者小红书的链接，它帮你把视频图文转成本地的 Markdown，还能在原文之上再生成一层「速览」，重点高亮、金句卡片、脉络大纲，一屏抓住重点，随时切回去看原文。做到 0.6 了，命令行、网页端、Mac 桌面客户端、还有一个抓博主清单的油猴脚本，四种形态。

但我今天其实不太想聊它是个啥。

我想聊的是，做完这一版，我陷进了一个挺别扭的自我怀疑里。

那个怀疑就是，从头到尾，我好像就只是个提 bug 的人。

先交代一下背景，我不是纯做开发的，更偏产品加上一点 AI 工程。代码我能读、能改，但让我从零手撸一个带转录、带网页、带桌面壳的完整东西，老实讲，我心里是没底的。所以这次我几乎把所有的「具体怎么实现」都交给了 Claude Code。

你想想看这个画面。我遇到一个问题，我不去想它该怎么解，我直接把它扔过去，「这里报错了，你看看」。它调研、它定位、它改、它给我跑测试。我再去点一下，发现还有问题，我又扔回去，「还是不行，这是新的报错」。

来来回回，我手里好像一行解决方案都没出过。

愚钝如我，搞到后面我真的开始慌了。我寻思，那这个产品到底是我做的，还是它做的？我是不是就是个甩手掌柜，连甩手掌柜都算不上，我连「该往哪甩」都没怎么管，我就是个……报警器？哪里坏了我响一下。

这种感觉，说真的，不太好受。

但我后来把整个过程从头倒了一遍带子，倒着倒着，有点回过味来了。

回到最开始，这东西为什么长成现在这样。

它最早其实只是个「链接转原文」的工具，我自己用着用着，觉得不够。光把视频转成文字，那还是一大坨，我还是得自己读。我就想，能不能在原文上面再压一层精华出来，让我一屏就看明白。

这个「加一层速览」的决定，是我拍的。

而且我当时定了一条特别死的规矩，速览可以是 AI 提炼的、有损的，但它必须老老实实锚定回原文的坐标，绝对不许编造原文里没有的话。忠实原文那一层，必须无损，一个字都不能丢。

这条规矩，Claude Code 没有替我定。它如果自己发挥，很可能就给你「智能总结」一下，怎么顺怎么来，谁还管你锚不锚定原文。是我把这条红线钉死的，因为我太知道，一个会编造的笔记工具，对我这种拿它存知识的人来说，是负分。

你看，方向是我定的。

再往后是调研。模型怎么选，用哪个 ASR、哪个视觉模型、哪个大模型，多少钱一条。这块我确实大撒手，我就一句话，「去查查现在哪个最便宜，全球范围比一下」。

然后 Claude Code 吭哧吭哧给我拉了一张全球比价回来。结论挺有意思的，我现在用的这套组合，已经差不多是全球最便宜的档位了，那个所谓「每天循环白嫖免费额度」的路子基本不成立，唯一能薅的是某家的免费层，但走它会丢掉说话人分离这个我挺看重的功能。

调研是它做的。但「那就不换了，维持现状」这个判断，是我下的。它可以把账算得明明白白，可到底值不值得为了省那几毛钱去折腾、去牺牲一个功能，这个权衡它替我做不了，因为那是我的偏好，不是一道有标准答案的数学题。

到这我已经有点感觉了，但真正让我「卧槽」的，是并行开发那一段。

这块得稍微展开聊聊，因为它直接带出了我憋到现在没想通的一个问题。

桌面客户端那一摊，工作量很大，前端好几个屏、后端一堆接口。我当时想偷个懒求个快，就在本地起了好几个 Codex，接的是本地一个跑得飞快的小模型，让它们并行去写。一千多 token 每秒，那速度，看着是真爽。

一开始确实爽。那些独立的、全新建的文件，比如前端的几个屏、一个工具库，它哐哐哐一波就给你写出来了，质量还过关。我心想，这下赚到了。

然后我就笑不出来了。

凡是碰到那种「要去改一个已经很复杂的老文件」「要做结构性重构」的活，它就开始翻车，而且是反复翻车。有一个任务，它吭哧吭哧烧了五十多万 token，活没干成，还顺手把一个核心文件给我改坏了，提交都没提交，你敢信？？？还有一次，遇到带中文的文件，它直接就崩了。

我当时是真懵。。。给我一下子整不会了。说好的飞快呢，怎么越到硬骨头越拉胯。

后来我让 Claude Code 专门去把这个事刨了个底朝天，刨出来的根因，刷新了我的认知。

它跟我说，这事还真不怪那个小模型笨。问题出在工具层。Codex 改文件靠一个叫 apply_patch 的工具，而它给不给你这个工具、怎么给，是按模型的名字去一个内置名单里查的。我用的那个小模型，压根不在名单里，于是它根本就没被发上这把趁手的工具。拿不到工具的它，要么干脆用散文跟你聊半天啥也不改，要么硬憋出一个语法错的补丁。再叠加上那个中文崩溃的毛病，对我这么一个中文知识库项目，简直是天敌。

也就是说，它快、它笨，都不是重点。重点是它跟主控之间那根「线」，本身就接得不牢，而且会悄悄断掉，断了你还不一定知道。

对照之下，我用 Claude Code 自己的 Dynamic Workflow 去并行，体验完全是另一回事。它是用一段确定性的 JS 脚本，去编排好几个同家族的子 agent 一起干活。digest 那个最绕的锚定引擎、还有最后收尾那一波修 bug，都是这么干的，顺得不行，当场抓出十几个问题，几乎零返工。

我后来琢磨出的差别是这样的。Dynamic Workflow 派出去的那些 agent，跟主控是同一个运行时，同一套改文件的工具，同一本规则书，同一个模型家族，写完结果直接流回来当场就能验。而我那一堆 Codex，是另一个进程、另一个模型、另一套会卡壳的工具，全靠我喂过去的一段文本和一条事件流连着。一边是同物种内部协作，一边是隔着一道玻璃墙喊话。

这个发现挺反直觉的，我一开始还以为是「上下文给得多不多」的问题，结果根本不是。

回到我那个自我怀疑。

并行这一段，写代码的全是 AI。可你发现没有，是我撞上了「Codex 反复翻车」这个现象，是我觉得不对劲、是我决定停下来去刨根因。AI 自己跑得正欢，它不会停下来问自己「我是不是这套工具就不该这么用」。

然后是最后的调试，这一段最能说明问题。

桌面客户端做出来，我兴冲冲打开，一转录就 400。我把报错甩过去。查了半天，根因特别阴间，我在设置页面把某个输入框留空保存了，结果它把模型配置写成了一个空字符串，而代码里取配置的时候，空字符串它不当「没填」处理，于是模型名就成了空的，请求自然 400。

这种坑，AI 自己永远撞不出来。因为它不会真的去点我那个设置页面，不会鬼使神差地把一个框留空再保存。

还有更绝的。我改完一段 Python 源码，重启 app，发现一点没变。又是一通找，才发现桌面端跑的根本不是我的源码，是一个提前冻结打包好的二进制，我不重新打包，改了也白改。还有一次，转录报模板找不到，原因是打包的时候漏把一个模板文件塞进去了。

这些全是「真实世界」才会给你的耳光。AI 活在一个干净的、理想的环境里，它跑测试全绿。可测试全绿，跟真有个人在一台真机器上点崩它，是两码事。

那个去真机上点、去把它点崩、去把报错原原本本捞回来的人，是我。

聊到这，我那个别扭的自我怀疑，慢慢变成了另一个东西。

我开始怀疑，「提 bug 的人」这个角色，会不会恰恰是这里头最不能被替代的那个？

你看啊。方向是我定的，AI 不会替你拍板要不要坚持一条让自己更累的红线。它调研错了的时候是我纠正的，有一次它信誓旦旦跟我讲发布流程该怎么走，讲错了，是我凭着对这个项目的了解把它拽回来的。真实世界的坑是我用身体撞出来的，因为它没有身体。

它负责的是「怎么做」，而且做得比我快得多、好得多。

我负责的是「做什么」「做对了没」「在真实世界里它崩没崩」。

当「执行」这件事变得越来越不值钱，瓶颈就悄悄挪到了「判断」和「提出对的问题」上。我一直觉得，提出一个好问题，有时候比解决它还难。一个外行能不能用好 AI，可能不取决于他会不会写代码，而取决于他是不是有品味、知道什么是对的、并且愿意在一片「测试全绿」的虚假繁荣里，固执地点开真机，去找那个还没暴露的 bug。

我说「可能」「也许」，是因为我自己也还在摸索，这套想法还远不成熟。

我甚至不敢说我这个结论是对的。万一过两年，AI 自己也能开虚拟机、自己点 UI、自己撞真机的坑了呢？那我这个「提 bug 的人」的护城河，可能一夜之间就没了。

所以我没法给你一个漂亮的收尾。

我反而想老老实实地，把我自己到现在都没想通的三个问题，摆在这儿，征集一下屏幕前的你的看法。如果你也在用 AI 做东西，特别想听听你怎么看。

第一个。Claude Code 的 Dynamic Workflow，跟我自己开一堆 Codex 并行，到底该怎么选？我前面讲了我刨出来的根因，但我还是没想透，是不是只要把那根「线」接牢，比如换个名单里有的模型、绕开中文崩溃，多 Codex 并行就能追平甚至反超？还是说，跨进程、隔玻璃墙喊话这个事，天生就有损耗，结构性的硬活就该老老实实留在同一个运行时里干？你们的实战经验是啥。

第二个，这个问题特别困扰我。同样一套设计系统，同样的配色、圆角、品牌，我的网页端做出来挺好看的，可桌面客户端，用 Tauri 做的那个，精致程度就是差那么一截，说不上哪不对，就是没那个味儿。我不知道是 webview 的渲染差异，是我没给桌面端单独调，还是别的什么玄学。做客户端 UI 的朋友，这事你们怎么破的？

第三个。Rust 加 Tauri 的开发成本，我体感是显著高于 Python 加网页端的。一边是改完刷新就看见，一边是动一下要重新编译、重新打包、重启。我不知道这是我姿势不对，还是这俩东西的差距就是这么大，大家都是怎么扛过来的。

这三个问题，但凡你有一条想法，都欢迎在评论区把公屏打给我。

红蓝CP 我已经全部开源了，连这一路的设计、调研、踩坑、和 AI 怎么协作的开发日志，都摊开放在里面了，地址是 github.com/MuChengZJU/red-blue-cp。不是为了让你来 star，是真觉得，一个不太会写代码的人，靠不停地提问、纠错、和去真机上挨揍，能把一个东西做出来，这个过程本身，可能比那个产品更值得聊。

我又想起昨天半夜那句「还是不行」。

现在再看，那四个字好像没那么窝囊了。

它至少证明了一件事，我还在真的用它，真的在乎它到底行不行。而这件事，目前为止，还得靠一个活人来干。

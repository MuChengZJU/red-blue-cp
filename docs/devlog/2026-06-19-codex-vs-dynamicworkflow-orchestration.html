Codex(mimo) 并行 vs DynamicWorkflow(Opus) 并行

V0.6 复盘 · 2026-06-13~18 四会话 · 运行时/提示词结构与稳定调用
一句话: 不是「mimo 代码能力差」。主因是 运行时/工具带不匹配 + 一个真实的计划级契约缺陷。 Codex 的 apply_patch 按 model-slug 查内置 catalog 决定实现,mimo 不在 catalog → 根本没被注入 apply_patch 工具和 V4A 指令,再叠 CJK 字符 panic、中途预算静默停。 而 DW 顺,是因为它的子 agent 和主会话同一个运行时:同一个 Edit 工具(unicode 安全/原子写)、同一本规则书(CLAUDE.md)、同模型家族(Opus)、结果回流即验。 差距在「同物种同工具带」vs「异物种自带会卡的工具」,不在「上下文多少」。

② 失败归因:计划 vs 执行(重证据)

任务包写得非常细(契约/字段/边界/验收命令俱全)。「光是计划不够细」基本被证伪。

失败性质根因
task 1.0 sed 改坏 pipeline.py(烧 587k 没 commit)计划+执行任务包两条约束自相矛盾(文件白名单 vs 不许新增失败测试,在 test_proxy_passthrough 上互斥)→ sed 硬解改坏
task 1.2 最难重构没做(停"Step 3")执行/运行时一包塞太多,做完前两步 token 预算到了就停、没 commit。拆小后即过

纯模型能力锅几乎没有。 成功轴=独立/纯新建/无特殊字符/不碰复杂既有文件;失败轴=结构性重构 + 特殊字符(独立失败轴)。

③ 代码层 + 提示词层:四种机制到底差在哪

提示词层(上下文怎么拼)代码/特性层(控制流·工具·上下文管理)
① CC 主会话系统提示 + 全局/项目 CLAUDE.md + 按需 Skill + 全量累积会话历史单窗口,长了自动压缩;Read/Edit 工具
② CC 子 agent自己的精简系统提示 + 单条 prompt + CLAUDE.md 在场;不继承会话历史主模型即兴决定派不派;只回传最终消息(上下文防火墙);每 agent 全新窗口
③ DynamicWorkflow每个 agent() prompt 写死在 JS 脚本里 + 可带 JSON Schema(校验失败自动重试);默认继承 Opus控制流是确定性代码(parallel/pipeline/循环);脚本只攥结构化返回(小)→能 scale;内建对抗验证
④ CC→CodexCodex 自己的 base 指令 + AGENTS.md(不读 CLAUDE.md) + 管道喂的任务包;XML 块结构另一个进程:自己的 loop、apply_patch 按 slug 接线、自己的 sandbox/预算;CC 只看 JSONL 事件流
  • ①②③ 同一运行时,只差控制流(一窗口/主模型派/代码编排)和上下文范围(累积/每 agent 全新)。
  • ②③ 跟 ④ 的代码层差异不在上下文,在工具带:②③ 用同一个 unicode 安全的 Edit;④ 的 apply_patch 按 model-slug 查目录接线,mimo 不在目录→工具压根没注入。这是代码层静默断线,提示词层看不见。
  • 纠正直觉:②③④ 都精简上下文起步、都不继承会话历史。差距是「同物种能自己 grep 补齐」vs「异物种补齐弱+工具会卡」。

④ 速度:端到端是「任务类型依赖」的

  • 甜区任务(独立/新建/无特殊字符):codex+mimo 端到端更快(6 屏一波拿下)。
  • 结构性/复杂既有文件/特殊字符:codex+mimo 端到端更慢——快速生成被返工吃光(1.0 烧 587k+手修、1.2 重发、收尾一整会话)。
  • DW-Opus:单位 token 慢但首轮成功率高、返工少,硬活上打平甚至更快。

mimo 的快只有在「甜区任务 + 严格验证」下才兑现成端到端的快。

⑤ 下一步:3 条实验(按依赖排序,不堆建议)

A · 前置闸门 ~10 行 spike

单跑一次 codex exec+mimo,做个必须改含中文文件并 commit 的小任务:mimo 拿没拿到 apply_patch?碰中文 panic 没?先 curl mimo 的 /v1/responses 看通不通。这条决定方向:不通就切「禁 apply_patch、强制 shell 整文件写」。

B · 正面对照 同任务端到端

选一个自包含真实任务,跑两次:DW-Opus 一路、codex-mimo 一路。量端到端墙钟(到测试绿+已 commit)+质量。用数据替代猜。

C · 自建稳定调用封装 核心欠债

官方 codex-rescue 是"单次转发器",不为并行开发设计。先写薄封装,最高杠杆=不信 exit 0、解析事件流:流以 turn.completed 收尾才算成 / 测试命令 exit_code==0 / file_change 真落盘 / git rev-parse 确认真 commit / 超预算或没 commit=未完成上报 / CJK panic 降级 shell 整写。(main 上 AGENTS.md 当规则书蓝本那个提交,已做了"喂规则书给 codex"的一半。)

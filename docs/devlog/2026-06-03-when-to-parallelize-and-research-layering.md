# 何时能并行开发 + 调研要分两层

> 复盘 P1 时想清楚的两件方法论:① 决定能不能并行的不是"PRD 全不全",是"**这个接缝的决策冻没冻**";② 调研要分**功能层**(冻哪儿)和**技术层**(冻得住吗)。给 PM 视角 + 工程视角各一份判断。

## 一、并行的本质:契约冻结,不是 PRD 完整

并行 = **两块活之间的边界已经定死,各做各的不互相等**。这在每个层级都成立(跨特性、跨模块、一个特性内部)。

**关键纠偏**:不需要**整个 PRD** 做完才能并行;只要**某一个接缝**冻住,它下面的活就能 fan out。

> 本项目活例子:博主全量这个**特性是串行试出来的**(brainstorm→设计→Codex 三轮),但契约一冻(Phase 0 的 dataclass + fixture + SPEC §4.4),**下面的实现立刻并行**(A/B/C 三个 subagent)。**串行的是决策,并行的是决策之下的执行。**

## 二、两种"串行",区别对待

| 类型 | 长啥样 | 能并行吗 |
|---|---|---|
| **依赖链** | 上线→试用→反馈,**反馈就是下一个需求的输入** | **真不能**。没法并行"还没发生的反馈" |
| **单点未决** | 一个决策还没拍,但不依赖别的结果 | **能**,但是"并行试 N 个方案再挑一个",拿返工/token 换速度/质量 |

迭代式 PRD(用一次、改一次)属于**依赖链**——天生串行。而且**在依赖链上硬并行是负价值**:并行 3 个方向,反馈一来发现方向错,扔掉 2 个,还白踩并行的合并坑。所以**探索期串行是对的,不是凑合**。

## 三、PM 的最高杠杆:不是写更大的 PRD

是**尽快把"已经想清楚的那部分"在对的接缝上,显式冻成契约**。每冻一个接缝 = 开一个并行口子。

- 全局还在探索 ≠ 处处不能并行;某个**已经定死的子模块**照样能冻了并行。
- 提效率不是逼自己一次写全 PRD(探索期反而浪费),是练**"识别哪个接缝够稳、可以冻"的眼力** + 把它冻得干脆(可执行,像 Phase 0)。

## 四、调研分两层,接到"冻契约"上

- **功能调研**(用户要啥、边界):喂"**该冻哪些接缝、按什么形状冻**"。这是探索,串行。
- **技术调研**(选的方案到底能不能干那个具体的事):验"**这个接缝冻下去,底下建得出来吗**"。

**铁律**:技术调研要在"**冻契约 + fan out 之前**",针对那个具体依赖做个小 spike。

> 反例:pydoll 那次只调研了"它能连 Chrome"(功能层),没验"它注入的钩子能不能抓到页面请求"(技术层)。结果冻完契约、agent 都派出去了,执行期才发现抓 0,返工改原生捕获。

## 口诀

> **功能调研决定"冻哪儿",技术调研保证"冻得住";两个都过,才下并行。**
> **能不能并行,只问一句:这个接缝的决策定死了没?定了→并行执行;在依赖链上还没定→老实串行。**

# 用户实测连环修（0.5.1/0.5.2）+ 插件油猴分发（0.3.x）

> M5b 发版后，用户在真机连续用、连续暴露问题，一轮轮修到稳。最值钱的是抓清单插件的根因（首屏 SSR vs 翻页 XHR）+ 分发方式从「加载已解压」演进到油猴脚本。全程「探针实证结构再写代码」，不凭记忆赌爬虫目标的字段。

## 主程序连环修

- **0.5.1 旧批次回填**：0.5.0 把批量条目改成「逐条建 job」后，**升级前**的旧批次条目没有 job → 点不进详情、没标题，且断点续传会跳过已完成条目永远补不上。修：打开库时给历史 done/failed 条目回填 job + 关联，标题用 md 文件名兜底，幂等。连带修去重盲区（升级前下过的也参与去重）。
- **0.5.2 标题去渣 + 批次费用**：0.5.1 回填把整个 md 文件名当标题（带日期/作者/note_id）。修：`_title_from_md_stem` 剥日期前缀/尾部 id/作者段，标题位是 note_id 占位 → None 诚实显示 id；已写入脏标题的库启动时再洗一遍（item+job 同步）。批次卡片加费用汇总（只算有账任务——历史任务在记账功能 0.4.1 之前下载、补不出账，诚实空白）。

教训：**「逐条建 job」这类把旧数据接入新模型的改动，迁移要覆盖存量**——只想着新数据，旧批次就成了点不进去的死条目。

## 插件：抓清单根因 + 油猴分发

### 根因：首屏 SSR，不发翻页请求

插件原来只 hook 翻页的 `user_posted` 网络请求。但博主主页**第一屏笔记是服务端直出**的，藏在 `window.__INITIAL_STATE__.user.notes`，不发请求。笔记少的博主一屏到底、滚动不触发翻页 → 一条没抓到，popup 显示「请滑动」。日志里**没有任何 `XHR 本页 N`** 是铁证。

修复用探针实证了真实结构（不靠记忆）：
- `user.notes` 是 **Vue ref**，真数组在 `.value`（前一版探针没解包，误以为是 object）
- item 字段是**驼峰** `{id, noteCard, xsecToken}`，而网络请求是**下划线** `{note_card, xsec_token}`

→ `seedFromInitialState` 读 `.value`（解包+flat），`ingest` 两种命名都认。这是 app 自己的笔记仓库，不管首屏/翻页/换接口都在，比 hook 网络更稳。两个博主实测：小号补抓 21 条、大号补抓首屏 30 + 翻页累计 309，note_id 去重正常。

### 分发：油猴脚本 > 加载已解压 > 上商店

用户嫌每次手动加载麻烦、问能不能上架。判断：
- **上公开商店**（Chrome/Edge）：抓取类扩展有审核拒/事后下架风险，且要把描述写到失真——与「能力照开源、去对抗措辞」的原则冲突。否决。
- **油猴脚本**（采用）：Tampermonkey 本身可信已上架，脚本只是它加载的文本，不经审核、不会下架、零费用；`@updateURL` 指向 GitHub raw → 自动更新，彻底解决「每次麻烦」。页内悬浮面板替代 popup（折叠成 40×40 小方块）。
- 技术关键：`@grant none` 跑页面主世界 + `@run-at document-start` 才能 hook `window.fetch`；XHR 改原型最稳；主数据源是 `__INITIAL_STATE__`（零网络）。实测大小博主都稳。

### 版本策略（定档）

- **油猴脚本 + MV3 扩展共用核心 → 共用版本号**（现 0.3.1），一起 bump。油猴 `@version` 必须升才触发自动更新。
- **rbcp 主程序独立计版**（现 0.5.2）。
- 真正的跨工具契约是 **`schema_version`**（notes.json 格式，现 `1`，与 `service/batch.py SUPPORTED_SCHEMA_VERSION` 对齐），格式变才一起动。

## 方法论沉淀

- **爬虫目标的结构必须探针实证再写代码**——本轮两次探针修正了我的假设（notes 是 ref 不是 object；字段驼峰不是下划线）。凭记忆写映射会错。
- **诚实优于假完整**：补不出的历史账单、无法确认的「是否到底」，如实标「部分」「估算」，不造数据、不假装。
- 控制台噪音排除：属于插件的只有 `[RBCP 清单]` 开头的行，其余是小红书页面 + 其他插件 + 反爬探测。

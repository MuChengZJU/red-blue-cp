# M5b 交付 0.5.0：WebUI v2——单条/批量整合、批次进任务列表、去重检测

> 本轮先在 PLAN 里写好 **Eval（E1-E12 验收清单）** 再动手，完工=逐条核验过。
> 单流 TDD，一个 PR（#37）。前后端耦合（storage/routes/templates 串改），不并行。

## 范围里的一个关键架构决策

「批次进任务列表 + 条目可进详情」字面看是前端需求，实际依赖一个后端事实：
M4 的批量条目（batch_item）**不创建任务记录**，所以没有详情页可进、没有用量账单、不能重试。

决策：**批量逐条建 job**（`batch_item.job_id` 关联），详情/账单/重试全部复用任务体系，
不为批量另造一套展示。代价是两套状态（batch_item + job）要保持一致，靠测试锁住。

## 交付内容

- **去重检测（E1/E2）**：`urls.dedup_key`——B 站 BV 号 / 小红书 note_id 归一，
  token/追踪参数不同也认得出同内容；短链（b23.tv/xhslink）解析不出 id 老实返回 None 不猜。
  单条提交已下过 → 409 + 旧任务信息 → 前端弹「是否重下」；批量导入默认跳过已下过并报数。
- **批次取名（E3）**：batch.title（导入时可自定义，缺省「博主 xxx · N 条」）。
- **批量建任务（E4）**：run_batch 每条 create_job → mark_done(含 usage)/mark_failed；
  重跑时条目已有 job 则 `reset_for_retry` 原地重置（不新建）。
- **WebUI（E6-E9）**：主页两标签；`/batches` 301 回主页；批量导入交互重做；
  批次卡片（标题/进度条/计数/前 5 条可滚/展开全部/条目进详情）；
  `/api/jobs?exclude_batched=true` 让批量任务只住批次卡片不重复显示。
- `rbcp serve --port`（E12，上轮发现的写死 8000）。

## Codex review 修 2 项（含 1 个 P1 安全项）

1. **P1 批量 job 重试绕过代理**：批量条目变成 job 后，UI 的「重试」走单条管道，
   而单条管道不读 `RBCP_PROXY`——护 IP 场景下重试会暴露真实 IP。
   修：WebUI 管道统一改走 `pipeline.fetch_single` 并吃 `RBCP_PROXY`。
   这类「新特性把旧路径接到新场景，旧路径的假设失效」是独立 review 最值钱的猎物。
2. **P2 重跑孤儿 job**：每次重试新建 job 并覆盖关联，旧 job 漏进主任务列表。
   修：原地重置复用（与单条「重试不新建」哲学一致）。

## Eval 先行的体感

把验收写成 E1-E12 再开工，两个好处实测成立：
- 实现时不纠结边界（「短链怎么办」「失败的旧任务拦不拦」在写 Eval 时就定了）；
- 收尾核验有清单可勾，浏览器实测不会漏场景（弹窗确认后真重下、导入全重复清单的提示语，都是按清单逐条跑出来的）。
